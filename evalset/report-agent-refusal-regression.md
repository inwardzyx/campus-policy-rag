# Agent 拒答回归验收报告

> 目的：接了 agent（MCP + 工具 + 多轮循环）之后，**模型会不会在「库里没有」的情况下硬编答案**。
> 本文件由 `agent/render_regression_report.py` 从实测 JSON 生成，**数字非手写**。

## 一、结论

- **发现硬答 6、5、4 题**：工具已经明确说了「库里没有」，模型仍然编了答案出来。这才是本次验收要找的回归。
- 硬答率（主指标）：**10.5%~15.8%（3 次：15.8% / 12.5% / 10.5%）**　（6、5、4 题 / 每遍）
- 跑了 **3** 遍；全部请求错误数 **0**（错误不计入分子分母，另计——把服务异常算成拒答能力差是口径错误）

## 二、主指标：硬答率（结构化信号）

| 指标 | 数值 | 含义 |
|---|---|---|
| agent `no_hit` 信号占比 | 65.5%~69.0%（3 次：65.5% / 69.0% / 65.5%） | 工具明确回报「库里没有」的题占比 |
| 直打 `no_hit` 信号占比 | — | 同一批题走直打路径时的占比（用于对照） |
| **硬答题数** | **6、5、4** | 拿到 `no_hit` 却仍然作答 |
| **硬答率** | **10.5%~15.8%（3 次：15.8% / 12.5% / 10.5%）** | 硬答题数 ÷ `no_hit` 题数 |
| 信号解析失败 | 9 | 这几遍里**模型一次工具都没调**（`n_tool_calls=0`），所以没有任何工具输出可解析 —— **不是协议故障**。它们是能力边界题（天气 / 奶茶店 / 饭店），模型直接答「我帮不上忙」。**独立报出，既不并入 no_hit 也不并入硬答** |

### 为什么主指标不用「拒答率」

因为关键词判据做不到低假阳率。实测反例（`agent/probe_toolnode_errors.py` 同源探针）：

> 「我查不到具体的报销比例，但按往年惯例一般可以报销 80% 左右。」

这句是**硬答**（它编了 80% 这个数字），但只要判据里有「查不到」三个字就会判成「正确拒答」——**恰好把本次验收要找的失败模式洗白**。

所以现在的分工是：

| 层 | 数据来源 | 作用 |
|---|---|---|
| **主指标** | 工具返回的结构化 `hit_status` | 判定回归 |
| 辅助 | 模型答案文本（关键词判据） | 只报数，不判定 |
| 过程 | `n_tool_calls` / `rounds` | 观察行为 |

文本判据本次另有结论：agent 85.2%~88.5%（3 次：85.2% / 85.2% / 88.5%），其中 0 题判不出（空答案/工具错误提示等，已排除出分母而不是硬猜）。

### ⚠️ 直打侧的文本拒答率必须拆开看

直打侧合并文本拒答率 95.1%~98.4%（3 次：95.1% / 98.4% / 98.4%） 看着漂亮，**但其中大半不是模型拒的** —— `service.py` 在 rerank 最高分 < 5 时直接返回固定文本、**压根不调模型**：

| 遍 | 服务硬短路（未调模型） | 其中拒答 | 真调了模型 | 真调模型里的文本拒答率 |
|---|---|---|---|---|
| 1 | 40 题 | 40 题 | 21 题 | 85.7% |
| 2 | 42 题 | 42 题 | 19 题 | 94.7% |
| 3 | 39 题 | 39 题 | 22 题 | 95.5% |

⇒ 剔掉服务硬短路后，直打侧真实模型拒答率 85.7%~95.5%（3 次：85.7% / 94.7% / 95.5%），与 agent 侧同档。

⚠️ **只报上面那个合并数字会得出相反的结论**：它会让人以为「直打拒答能力 98% 以上、远胜 agent 的 89%」，而实际上三遍共 121 题的拒答是**服务替模型拒的**（占直打侧 66%），模型根本没被调用。


## 三、这个实验**不能**回答的问题

⚠️ **本报告不声称「接了 agent 之后拒答能力变好/变差」。** 三条原因：

**① 两侧不是只差一个 agent 层。** system prompt、模型实例、上下文构造、查询改写四处都不同 ⇒ 差值不能归因于 agent。

**② 直打侧有硬短路。** `service.py` 在 rerank 最高分 < 5 时直接返回固定文本、**压根不调模型** ⇒ 它的拒答里混着「服务替模型拒答」，与 agent 侧的纯模型行为不同源。

**③ 基线 39/61 是检索层口径**（出处：`evalset/report-rerank-heldout.md（在线层/rerank，产品默认）`），与本文的文本层数字**不可相减**。

⇒ 要真正回答「agent 层有没有影响」，正确设计是**固定生成侧不动**（同 prompt / 同模型 / 同 top_k / 同上下文格式），只替换「检索结果如何进入生成」这一处。这是下一步，不是本次的结论。

## 四、应答能力

_本次只跑了拒答题集（`--only-refuse`），应答侧无数据。故不渲染表格：0/0 会显示成「0.0%」——看起来像「应答能力全军覆没」，而真相是没测。_

## 五、判据本身被推翻过三次（这部分比数字重要）

| 版本 | 缺陷 | 它会造出的假结论 |
|---|---|---|
| v1 裸关键词 | 正确答案里的否定表述被判拒答 | 「agent 拒答能力崩了」 |
| v2 有依据优先 | 声明查不到 + 贴条款被判作答 | 「掉了 24 个百分点」 |
| v3 三段式 | `_EVIDENCE` 是**死代码**（两个出口都是 False） | 注释写的机制根本没实现，实际跑的是 v1 |
| **v4 起（本次）** | 文本判据降级为辅助，主指标换成结构化信号 | — |

★ **v3 那条是本次最贵的教训**：注释里写着「三段式，二者不再互相短路」，而代码是

```python
if has_ev:
    return False
return False          # 两个出口相同 ⇒ has_ev 从未影响任何分支
```

⇒ 用例自检全绿也没能发现它，因为**用例只验输出、不验分支是否可达**。
发现它的是一次**独立盲审**（不看我的结论、直接读代码）。

判据现有自检 **21** 条常规用例 + **2** 条空答案用例 + **5** 条「已知判不准」用例，全过即拦提交。其中后者的期望值本身就是信息：

- 期望 `拒答/作答` ⇒ 判据在这个形态上可信
- 期望 **`无法判定`** ⇒ 真的分不出来，该题**排除出分母**而不是硬猜

### 四个判不准的形态（按误判方向分类）

| 形态 | 判成 | 方向 | 处理 |
|---|---|---|---|
| 正确依据里含「不包含个人」 | 拒答 | ⚠️ **危险**（会把硬答洗白） | 已加主体约束修好 |
| 因果收尾式拒答 + 补充说明 | 作答 | 保守（低估拒答率） | 已加 `_REFUSE_CAUSAL` 修好 |
| **「帮不上忙」+ 建议句带数字** | 作答 | 保守（低估拒答率） | 第五批修好，见下 |
| 空答案 / 工具错误提示 | 拒答 | ⚠️ 虚高 | 改为**第三态 `None`** |

### ★ 第五批盲审：又抓到 1 处，且暴露一个更麻烦的问题

跑完 3 遍后逐条读 r24 的原文，发现它**本来就是一条正确拒答**（「这个问题我帮不上忙——我只能查学校的公开制度文件，里面没有…」）却被判成作答。根因：`帮不上忙` 只命中 `_REFUSE_STRONG` 而不属于`_REFUSE_CAUSAL`，于是压不过建议句里的「20人」（`_has_substance` 命中）。

★ **这与已修的两条是同一形态** —— 说明第六版只修了「没法告诉你 / 查不到」那一半措辞，漏了「帮不上忙」。⇒ 词表修法只能止血：同一个意思换个说法就又漏了。这也是主指标必须换成结构化信号的理由，文本判据只配报数，不配判定。

⚠️ **顺带查出一个更严重的问题**：上一轮我说「已用当前判据重算写回」，其实只重算了 `per_question` 的逐题结果，`runs[].direct.refuse` 那份**汇总块从没被覆盖** ——
于是一份报告里同时存在两套数字（直打侧 46/61 与 58/61）。已改为渲染时统一调 `score_refuse` 从逐题重算，不信存好的汇总。
