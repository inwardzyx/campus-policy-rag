# Token 计量：两条路径都量到了，以及一个被推翻的直觉

> 生成方式：`agent/token_cost.py` 实测 20 题（10 道应答题 + 10 道拒答题）。
> 数字来自 `agent/_token_cost.json`（中间产物，按 `.gitignore` 不进仓库，
> 重跑脚本可再生成）。本文件里的每个数字都能对着下面写的命令复现。
>
> ⚠️ **本文件在 2026-10-12 被整篇重写过一次。** 上一版写着「直打侧未完成，
> 根因已定位」，那一版已经过期 —— 见下面〈三、上一版错在哪〉。

## 一、结论先说

| 路径 | token 计量状态 |
|---|---|
| **走 agent**（MCP + 工具 + 多轮循环） | ✅ 已完成，20/20 题全部拿到 usage |
| **直打 `/chat`** | ✅ 已完成，20/20 题全部拿到 usage，`missing_calls` 全 0 |

**两条路径现在同批可比**，这也是上一版拿不到的东西。

**一个比"贵一倍"更值得说的发现：拒答并不便宜。**

| | 题数 | 平均 input | 平均 total |
|---|---|---|---|
| 硬短路拒答（没调生成） | 7 | 634 | 784 |
| 调了生成作答 | 13 | 831 | 1049 |

拒答只省下生成那一次的 **output**，**input 一分没省**（634 / 831 = **76%**）——
因为拒答之前的**查询改写**和 **rerank 打分**两次调用一次都没省掉，
而 rerank 要把候选块的**全文**塞进 prompt 里。

更极端的一例：我故意打了一道库里没有的「GPA 怎么算」，

```
usage={'input_tokens': 1650, 'output_tokens': 146, 'n_calls': 2}
answer='知识库里没有能回答这个问题的资料，我不编。'
```

**这一次拒答花了 1650 token 输入**，比这批里答对任何一道题都多
（应答题最高 1557）。原因不是模型话多，是**为了确认"库里没有"，
先得把候选块全文读一遍**。

⇒ **"拒答很便宜"这个说法，在本项目里是错的。** 省token 的杠杆不在"让模型少说话"
（output 只占 20%），在**压缩检索侧输入**。

**数据质量自检**（这三条比均值本身更重要）：

- `missing_calls = 0` —— 直打侧 53 次 LLM 调用（13×3 + 7×2）全部返回 usage，
  没有一次靠估算或补 0。

### 这组数字里最值得说的四点

**① 接了 agent 之后每题贵 1.99 倍 —— 但贵在 input，不在"话变多了"。**
agent 侧 input 均值 1664、直打侧 762，**input 多 118%（2.18 倍）**；
而 output 均值 242 对 195，**只多 47 token**。
多出来的是每轮把工具结果（检索块全文 + 精排分）重新塞回上下文。
⇒ 优化顺序很清楚：**先压工具返回的体积**，而不是让模型少说话。

**② agent 侧缓存命中率 66.5%（cache_hit 合计 22139 / input 合计 33281）。**
system prompt + 工具 schema 那部分本该几乎全命中，实测每题仍有 512~574 token 没走上缓存。
合理解释：每题问的内容不同，**变化的user 消息打断了前缀**，
缓存只能命中 system prompt + schema 那一段。

**③ agent 侧 output 只占 12.7%（242/1906）。**
这个比例决定了优化方向：**省 token 的杠杆在 prompt 和检索结果压缩上，
不在"让模型少说话"上。**

**④ 成本 0.0033 元/题，20 题合计 0.065 元。**
按 DeepSeek 官方价（2026-10：缓存命中 0.2 元/M、未命中 2 元/M、输出 8 元/M）。
⚠️ **价格会变，成本数字会过期，token 数字不会。**
所以 `token_cost.py` 把两者分开报 —— 投递时只须换价格表即可重算，
token 部分永远是实测值。

## 三、上一版错在哪（保留下来是因为它是个典型）

上一版（本文件的前一版）写着「直打侧未完成，根因已定位，不是脚本 bug」。
结论方向没错，但**给出的证据是错的**，而且它靠那个错误证据得出了一个错误的待办。

**错误 1：把"响应里没有 usage 字段"当成根因。**
上一版贴的响应键是 `['answer', 'sources', 'took_ms', 'rerank_used', 'knowledge_hit']`，
据此说"服务端就没返回 usage"。但那份响应是**旧代码**打的——
当时 `usage` 字段还没加上，"没有"是理所当然的，
不能拿来证明"加了之后会很难拿"。

**错误 2：待办第 3 条写"★ 重跑一遍拒答回归"，理由是"服务改了，直打侧基线口径就变了"。**
这一条**是错的**，而且如果照做会白花 30 分钟。
理由：这次改动是**纯读取型** —— `_invoke_llm` 的返回值语义没变，
三处调用点仍然只取 `.content`，只是在旁边多读一个 `usage_metadata` 属性。
模型输入一个字符都没改 ⇒ **硬答率必然不变** ⇒ 回归不用重跑。

验证手段也不能选错：用"硬答率还在不在 10.5%~15.8% 区间"来证明"没变"是
**拿 5 个百分点的底噪当信号**，那个区间本来就覆盖随机波动。
正确做法是用 `agent/verify_direct_unchanged.py` 比对结构化不变量
（命中与否 / 引用了哪些条款 / sources 条数 ±1 容差），1 遍就够。
实测结论：✓ 不变量全部落在基线集合内 ⇒ 回归不用重跑。

## 四、这次改动踩到的真 bug：记账把三次调用记成一次

补计量的第一版代码**能跑、字段有值、不报错**，但数字是错的 ——
错得极其像合理的。分两层：

### 4.1 现象

服务重启后直打侧报 `usage={'input_tokens': 692, 'n_calls': 1}`，
而同一道题在进程内跑真实链路是 `input=1634, n_calls=3`。
**少算 58%。**

### 4.2 两个根因

| 位置 | 错误写法 | 后果 |
|---|---|---|
| `_record_usage` | `_LLM_USAGE.last = {...}` | 每次调用**覆盖**上一次 ⇒ 只剩"生成"那一次，改写+精排的 token 整段丢失 |
| `n_calls` | `getattr(_LLM_USAGE, "n_calls", 0) + 1` 塞进 `last` 字典 |那个**线程属性从没人写过** ⇒ 每次都读到 0 ⇒ **恒等于 1** |

一次 `/chat` 要调三次模型：**查询改写 → rerank 打分 → 生成**（`service.py`
的 `rewrite_query` / `rerank` / `answer` 三处都走 `_invoke_llm`）。

### 4.3 为什么第一轮没发现

因为这两个 bug **互相掩护**：覆盖之后只剩最后一次的数字，
而"1 次调用 + 一个小 input"看起来完全合理。我第一轮跑批就这么过去了。

只有两种办法能抓到：

- **让每次调用的 token 数不同**（假模型返回 100/200/300）——
  这样"覆盖"和"累加"给出的结果不同；
- **拿 `n_calls` 和真实调用链对账** —— 它是服务端自己数的，可核对。

⇒ 教训：**判据必须在"两种错误实现"下给出不同结果**。
如果每次 token 数都一样，覆盖和累加测出来完全相同，测了等于没测。

### 4.4 判据（5 条用例 + 3 个变异测试）

`tests/test_llm_resilience.py` 第 ⑥ 组。三个变异全部被抓，且**互不重叠**：

| 变异 | 报红的用例 | 说明 |
|---|---|---|
| ① 累加改回覆盖 | 4 条 | 覆盖 vs 累加被区分 |
| ② 只漏写 `n_calls` | 4 条 | 见下方"意外发现" |
| ③ 拿不到时清零已有账 | **只有** 1 条 | 精确命中"不该清零"那条 |

**意外发现（变异②）**：只漏写 `n_calls` 时，`_take_usage` 里 `if not acc or n == 0`
会返回 `None`，把**已经累加好的数据一起丢掉** —— 计数错了 ⇒ 数据全废。
好处是错得显眼，坏处是脆弱。没改，但记在代码注释里了。

**判据自己也被打脸一次**：我第一版断言写 `100*n` 的和，
手算成 300（实际 100+200+300=600），测试报红 —— **结果是我算错了不是代码错了**。
已改成显式写死 `(100,10),(200,20),(300,30)`，注释里记了"别在断言里手算"。

## 五、另一条不该被忽略的纪律：别拿弱判据当强判据

我一度判定"服务重启成功了"，依据是**响应里出现了 `usage` 字段**。
但旧代码也能满足这个条件 —— 它只证明"上一版代码在跑"，
不证明"这一版在跑"。真实标志是 `n_calls > 1` 且含 `missing_calls` 键，
旧代码给不出这两个。

⇒ 教训（与项目里那条"一个检查器绿灯时，要确认它真的检查了那些内容"同源）：
**判据要能区分"它抓到了"和"它本来就抓到了别的"。**

## 七、这套计量里守住的三条纪律

1. **取不到就返回 `None`，不填 0。** 填 0 会让"平均 token 数"变成假的，
   而**假的均值比没有均值更坏**（它看起来像答案）。
   本项目 agent 侧早就为这一条留了 `missing_usage` 那一栏，直打侧后来也补上了
   `missing_calls`。
2. **token 与钱分开报。** token 永久有效，钱依赖价格表、必然过期。
3. **不改正在被 import 的模块。** `token_cost.py` 里刻意重写了 20 行循环
   而不是给 `run_one` 加参数 —— 因为 `run_one` 正被跑批依赖着。
