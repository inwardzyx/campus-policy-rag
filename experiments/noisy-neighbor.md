# Noisy neighbor 实验：一个租户打满，另一个租户会被拖慢多少

> 2026-11-20 实测。结论先行：**共享 CPU 才是根因；按调用方限并发只能减少入口流量，救不了被拖慢的邻居。**
> 三个数：B 的 p95 从 **69.8ms → 647.3ms（+827%）**（无上限）→ **27.3ms → 233.4ms（+755%）**（加了按调用方并发上限）。

## 一、实验怎么做的

```text
服务：8036 单独实例（不开 AGENT），AUTH_MODE=proxy，ALLOW_CLIENT_ID_HEADER=1
租户：X-Client-Id 分桶（tenant-a / tenant-b）—— 诚实说明：这是"内部分桶"，不是租户鉴权
噪音源：/search（向量 + BM25 + 重排，CPU 密集）；不是 /chat（那个大头是等上游模型）
阶段：① B 单独 60s ② A 48 并发加入 60s（B 不停）③ A 停 60s
采样：keep-alive 长连接 + 每 10ms 一发；每请求记延迟与状态码
```

## 二、第一轮：没有并发上限（只有频率限流）

| 阶段 | 请求数 | p50 | p95 | p99 |
|---|---|---|---|---|
| ① B 单独 | 4,599 | 38.3 | **69.8** | 88.9 |
| ② A 打满 | 489 | 485.8 | **647.3** | 714.4 |
| ③ A 停 | 5,124 | 34.7 | **56.3** | 74.7 |

**B 的 p95 劣化 +827%**；A 自己也从 38ms 变 480ms（互相拖累）。
这是真实的 noisy neighbor：**一个租户的并发把共享进程的 CPU 吃满**。

## 三、第一版修复：按调用方并发上限（`MAX_CONC_PER_CALLER=2`）

| 阶段 | 请求数 | p50 | p95 | p99 | 429 |
|---|---|---|---|---|---|
| ① B 单独（2 并发） | 4,207 | 17.4 | **27.3** | 34.5 | 0 |
| ② A 打满（48 并发，被限到 2） | 686 | 157.5 | **233.4** | 315.6 | 22,318（A 侧） |
| ③ A 停 | 3,987 | 18.9 | **29.1** | 36.6 | 0 |

**B 的 p95 仍然 +755%**。

## 四、为什么这个修复没解决问题（关键结论）

按调用方限并发，限制的是**入口流量**（A 的 22k 请求被 429 挡掉），但**没限制住"两个并发请求各吃多少 CPU"**。
A 的 2 个请求照样能把单进程的 CPU 打满，B 的 2 个请求就只能排队。

```text
瓶颈定位：单 FastAPI 进程 + CPU 密集型检索（embedding / 重排）
⇒ 真正的隔离粒度不是"每个调用方几个并发"，而是"共享的 CPU 有几个执行单元"
```

**正确解（下一步，未完成）**：多 worker / 多副本（进程级隔离）+ 全局 CPU 并发上限（而不是 per-caller），
或者把 embedding 挪到独立进程/服务，让 /search 的 CPU 不与生成路径共享。

## 五、这轮实验的可复跑命令

```powershell

$env:ALLOW_CLIENT_ID_HEADER="1"; $env:GLOBAL_DAILY_REQ_QUOTA="100000000"
$env:MAX_CONC_PER_CALLER="2"; $env:AUTH_MODE="proxy"; $env:TRUST_PROXY_HEADERS="1"
D:\Python-project\.venv\Scripts\python.exe -m uvicorn service:app --host 127.0.0.1 --port 8036

# 2) 跑四阶段
D:\Python-project\.venv\Scripts\python.exe scripts\noisy_neighbor.py
```

原始数据：`experiments/noisy-neighbor.json`（逐请求延迟与状态码）。

## 六、这轮踩到的三个坑（都写在这里，避免重跑时再踩）

1. **401 污染**：`AUTH_MODE=proxy` 下不带 `X-Auth-Roles` 就是 401，8ms 返回——会把"基线"测成假的快；
2. **端口耗尽**：每请求新建连接，15 万次后 Windows 报 `WinError 10048`；改 keep-alive 长连接；
3. **全局配额打光**：默认 `GLOBAL_DAILY_REQ_QUOTA=2000`，压测 10 秒就打满，之后全是 503（`global_req`），不是性能问题。

## 七、面试可以怎么讲（诚实版）

```text
“我做了 noisy neighbor 实验：一个租户 48 并发打 /search，另一个租户的 p95 从 70ms 涨到 647ms。
我先加了按调用方并发上限——A 的 2.2 万次请求被 429 挡掉，但 B 的 p95 仍然 233ms。
结论是瓶颈不在入口流量，而在共享的 CPU：单进程里 2 个重请求就能把邻居拖住。
真正的解是进程级隔离（多 worker/多副本）或把 embedding 拆出去，这条我还没做完。”
```

**这段话的价值**：有测量、有第一版修复、有"修复无效"的诚实结论、有对根因的判断。
比“我做了多租户隔离”强得多——因为它连“我错在哪”都说清了。

⇒ **本报告沿用 48 并发那两轮数据**，并如实记下两点干扰：

2. 还有一整套 **Dify**（api/web/worker/sandbox，约 2GB 内存）。

## 九、第二轮（2026-11-20 晚）：把"正确解"做完 —— 结论是"多 worker 不是解药"

### 9.1 一句话

同一台机器上：**+652% → +472%**（只改服务端，客户端行为不变）→ **+178%**（客户端也尊重 `Retry-After`）。
而**"多 worker"单独做会让它变成 +845%**。

原因是 `MAX_CONC_PER_CALLER` 是**每进程**的口径：4 个 worker 会把"同时最多 2 个真实请求"
悄悄变成"同时 8 个"——那不是隔离，是把闸门复制了 4 份。

### 9.2 逐臂数据（每臂 4 阶段、每阶段 60s，与第一轮同口径）

| 臂 | 服务端配置 | B 基线 p95 | 噪音期 p95 | 劣化 | 噪音期 CPU | B 收到 429 |
|---|---|---|---|---|---|---|
| R0 现状 | 1 worker，端点里判并发（`ADMIT_MODE=endpoint`），cap2 | 38.8 | 291.9 | **+652%** | 86.3% | 0 |
| A5b 只加 worker | 4 worker，每进程 cap2，**无全局预算** | 19.2 | 181.4 | **+845%** | 86.2% | 0 |
| R2 worker + 每进程预算 | 2 worker，每进程 2（总预算仍 4） | 32.6 | 269.4 | **+726%** | 85.1% | 1 |
| R1 全局预算 | 1 worker，`GLOBAL_CONC=4`，受害者最多等 250ms，embedding 3 线程 | 16.1 | 92.1 | **+472%** | 57.7% | 0 |
| R3 = R1 + 客户端守规矩 | 同上，A 收到 429 后等 200ms | 34.0 | 94.7 | **+178%** | 61.1% | 0 |

★ **跨臂别比绝对值**：机器背景负载在臂之间漂（作者桌面 + Ubuntu 虚拟机 + Dify 栈，
每臂开始时空闲 CPU 23%–42%），"基线 p95"从 16ms 到 44ms 都有。可信的是**同一臂内**的配对比值。

### 9.3 三个发现

**① 多 worker 单独做，反而更差。** 见上表：+845% / +726% 都比现状的 +652% 差。
预算按进程复制 + 每次重启都要重新加载模型（4 worker 冷启动 4–5 分钟），两头不讨好。

**② 把预算收成"一个进程一个数"+ 让受害者排队而不是被拒 → +472%，且 B 一个 429 都没有。**
（`GLOBAL_CONC=4` 等于"同时最多 4 个检索在跑"，受害者拿不到名额时在**事件循环里等**，
不占线程；等不到才 429。见 `service.py` 的 `_EarlyAdmit`。）

**③ 但瓶颈不是"核被吃满"。** 噪音期 CPU 只到 57.7%，B 却仍慢 5.7 倍。
用 `/health`（完全不碰检索的轻接口）做对照探针：

| 客户端行为 | `/health` 噪音前 p50 | 噪音中 p50 | 放大 |
|---|---|---|---|
| 热重试（429 后立刻重打，≈1500 次/秒） | 3.3ms | 102.1ms | **30.9×** |
| 尊重 `Retry-After`（等 200ms） | 3.4ms | 10.1ms | **3.0×** |

一个**不查库、不算向量**的接口也慢了 30 倍 ⇒ 排队发生在**整个进程**（事件循环/GIL），
不是"检索路径算得慢"。这也解释了为什么继续调进程内的预算收益在变小：
风暴的粒度是"请求数"，而单进程每秒能处理的请求数是有上限的。

### 9.4 反例：让受害者排队"等太短"等于把它拒掉（B1 臂）

`GLOBAL_CONC=2` + `CONC_WAIT_MS=100`：A 一个人就能占住两个名额，结果 **B 自己收到 309 个 429**，
p95 反而 +921%。这种"受害者变快"是**假绿**——它不是被隔离了，是没拿到服务。
⇒ 要么留够份额（A 2 + B 2 = 4），要么等够久（≥ 对方一次请求的时长）。
这也是为什么 `CONC_WAIT_MS` 默认是 0（不等，立刻拒）：**要不要排队是部署决策，不能默认替用户做**。

### 9.5 测量工具本身被验证过（以及三条作废的数据）

我先怀疑"噪音源（48 线程）和受害者（2 线程）跑在同一个 Python 进程里，会不会是客户端在抢 GIL"。
把 A 拆成 4 个子进程重测同一台服务端：**同进程 +481%，分离进程 +466%** —— 差在噪声内，工具没问题。
这个怀疑**被证伪了**，记在这里，免得下一个人再花时间怀疑它。

作废的三条（`experiments/noisy-neighbor-round2.json` 的 `discarded` 字段里也记着）：

1. `A1`/`A5`：打到了上一轮没退出的旧进程上（新服务 bind 失败，测量照样出数，**最难发现的一种假绿**）；
2. `A0`：机器当时有 85% 背景负载（残留压测进程），只作方向性旁证。

⇒ 现在 `scripts/noisy_neighbor_round2.py arm` 会**核对监听者 pid 的创建时间**，不符就报错退出。

### 9.6 代码里落了什么（`service.py`，全部默认关或可回滚）

| 开关 | 默认 | 作用 |
|---|---|---|
| `ADMIT_MODE` | `early` | 准入在 **ASGI 中间件**里判（读 body 之前）；`endpoint` 回滚到第一轮的行为 |
| `MAX_CONC_PER_CALLER` | `2` | 同一调用方的并发上限（超出**立刻** 429：这类请求没有等的价值） |
| `GLOBAL_CONC` | `0`（关） | **每进程**同时允许几个 `/search`；忙时先让请求等 `CONC_WAIT_MS` |
| `CONC_WAIT_MS` | `0`（不等） | 全局名额忙时最多等多久（等待在事件循环里，不占线程） |
| `CONC_RETRY_AFTER` | `2` | 429 带的 `Retry-After` 秒数 |
| `EMBED_THREADS` | `0`（onnxruntime 默认=核数） | 每个请求可用几个 ONNX 线程；**多 worker 时必须设**，否则 4×14=56 线程抢 14 核 |

### 9.8 下一步：真正的隔离层在入口，不在进程里

| 候选 | 能解决什么 | 为什么这轮没做 |
|---|---|---|
| **入口层按租户限速 + 并发**（nginx/Envoy，或 Java 网关那层） | 挡住"请求数级别"的风暴，应用进程根本看不到 | 与"两个服务一台机器、Nginx 即网关"的既有决定一致，但要改部署；本轮只在应用层量 |
| Redis 全局计数器 | 让多 worker 共享**一个**预算（真正的全站口径） | 引入依赖（现在 Redis 连限流都只是可选），且本轮证明瓶颈不在这里 |
| embedding 拆独立服务/进程 | 隔离 CPU，让生成路径不被检索拖 | 多一跳网络 + 多一个部署单元，本轮数据看不出净收益 |

**一句话总结这一轮**：把"多 worker = 隔离"这个直觉证伪了；
真正的收益来自"**总预算按机器核数收敛 + 让受害者排队而不是被拒 + 客户端尊重 Retry-After**"，
而剩下的那 5 倍，得在**入口层**解决 —— 单进程内怎么调预算都有天花板。
