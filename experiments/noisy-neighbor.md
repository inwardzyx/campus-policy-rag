# Noisy neighbor 实验：一个租户打满，另一个租户会被拖慢多少

> 2026-11-20 实测。结论先行：**共享 CPU 才是根因；按调用方限并发只能减少入口流量，救不了被拖慢的邻居。**
> 三个数：B 的 p95 从 **69.8ms → 647.3ms（+827%）**（无上限）→ **27.3ms → 233.4ms（+755%）**（加了按调用方并发上限）。

## 一、实验怎么做的

```text
服务：8036 单独实例（不开 AGENT），AUTH_MODE=proxy，ALLOW_CLIENT_ID_HEADER=1
租户：X-Client-Id 分桶（tenant-a / tenant-b）—— 诚实说明：这是"内部分桶"，不是租户鉴权
噪音源：/search（向量 + BM25 + 重排，CPU 密集）；不是 /chat（那个大头是等上游模型）
阶段：① B 单独 60s ② A 48 并发加入 60s（B 不停）③ A 停 60s
采样：keep-alive 长连接 + 每 10ms 一发；每请求记延迟与状态码
```

## 二、第一轮：没有并发上限（只有频率限流）

| 阶段 | 请求数 | p50 | p95 | p99 |
|---|---|---|---|---|
| ① B 单独 | 4,599 | 38.3 | **69.8** | 88.9 |
| ② A 打满 | 489 | 485.8 | **647.3** | 714.4 |
| ③ A 停 | 5,124 | 34.7 | **56.3** | 74.7 |

**B 的 p95 劣化 +827%**；A 自己也从 38ms 变 480ms（互相拖累）。
这是真实的 noisy neighbor：**一个租户的并发把共享进程的 CPU 吃满**。

## 三、第一版修复：按调用方并发上限（`MAX_CONC_PER_CALLER=2`）

| 阶段 | 请求数 | p50 | p95 | p99 | 429 |
|---|---|---|---|---|---|
| ① B 单独（2 并发） | 4,207 | 17.4 | **27.3** | 34.5 | 0 |
| ② A 打满（48 并发，被限到 2） | 686 | 157.5 | **233.4** | 315.6 | 22,318（A 侧） |
| ③ A 停 | 3,987 | 18.9 | **29.1** | 36.6 | 0 |

**B 的 p95 仍然 +755%**。

## 四、为什么这个修复没解决问题（关键结论）

按调用方限并发，限制的是**入口流量**（A 的 22k 请求被 429 挡掉），但**没限制住"两个并发请求各吃多少 CPU"**。
A 的 2 个请求照样能把单进程的 CPU 打满，B 的 2 个请求就只能排队。

```text
瓶颈定位：单 FastAPI 进程 + CPU 密集型检索（embedding / 重排）
⇒ 真正的隔离粒度不是"每个调用方几个并发"，而是"共享的 CPU 有几个执行单元"
```

**正确解（下一步，未完成）**：多 worker / 多副本（进程级隔离）+ 全局 CPU 并发上限（而不是 per-caller），
或者把 embedding 挪到独立进程/服务，让 /search 的 CPU 不与生成路径共享。

## 五、这轮实验的可复跑命令

```powershell
# 1) 起实验实例（注意全局配额，默认 2000 会被压测打光 → 满屏 503）
$env:ALLOW_CLIENT_ID_HEADER="1"; $env:GLOBAL_DAILY_REQ_QUOTA="100000000"
$env:MAX_CONC_PER_CALLER="2"; $env:AUTH_MODE="proxy"; $env:TRUST_PROXY_HEADERS="1"
D:\Python-project\.venv\Scripts\python.exe -m uvicorn service:app --host 127.0.0.1 --port 8036

# 2) 跑四阶段
D:\Python-project\.venv\Scripts\python.exe scripts\noisy_neighbor.py
```

原始数据：`experiments/noisy-neighbor.json`（逐请求延迟与状态码）。

## 六、这轮踩到的三个坑（都写在这里，避免重跑时再踩）

1. **401 污染**：`AUTH_MODE=proxy` 下不带 `X-Auth-Roles` 就是 401，8ms 返回——会把"基线"测成假的快；
2. **端口耗尽**：每请求新建连接，15 万次后 Windows 报 `WinError 10048`；改 keep-alive 长连接；
3. **全局配额打光**：默认 `GLOBAL_DAILY_REQ_QUOTA=2000`，压测 10 秒就打满，之后全是 503（`global_req`），不是性能问题。

## 七、面试可以怎么讲（诚实版）

```text
“我做了 noisy neighbor 实验：一个租户 48 并发打 /search，另一个租户的 p95 从 70ms 涨到 647ms。
我先加了按调用方并发上限——A 的 2.2 万次请求被 429 挡掉，但 B 的 p95 仍然 233ms。
结论是瓶颈不在入口流量，而在共享的 CPU：单进程里 2 个重请求就能把邻居拖住。
真正的解是进程级隔离（多 worker/多副本）或把 embedding 拆出去，这条我还没做完。”
```

**这段话的价值**：有测量、有第一版修复、有"修复无效"的诚实结论、有对根因的判断。
比“我做了多租户隔离”强得多——因为它连“我错在哪”都说清了。
