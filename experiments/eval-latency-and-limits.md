# 评测耗时、延迟漂移与 429 静默污染（2026-10-27 实测）

> 起因：评审指出"调高 RATE_PER_MIN 能把评测从 5.3 分钟降到 1.6 分钟；README 的 2.8s 要站得住"。
> 本文是实测记录，不是估算。

## 一、干净的评测耗时（本机，单进程服务）

| 套件 | 题数 | 默认限流 | 墙钟 | 每题均摊 |
|---|---|---|---|---|
| campus | 20 | `RATE_BURST=10 / RATE_PER_MIN=20` | **63.2 s** | ≈ 3.1 s |
| hr | 24 | 同上 | **79.7 s** | ≈ 3.3 s |

结论：**干净跑一轮本来就是 ~1.1–1.3 分钟**，评审说的"5.3 分钟"在这台机器上复现不出来
（可能是把 429 重试/排队时间算进去了）。真正需要调高 `RATE_PER_MIN` 的场景是**连续跑多轮**。

## 二、连续跑时发生了什么（真问题）

同一服务（默认限流）连续跑三轮 campus：

| 轮次 | 墙钟 | 应答 | 现象 |
|---|---|---|---|
| 1 | 63.2 s | **15/15** | 正常 |
| 2 | **13.5 s** | **11/15** | 变快、变差 |
| 3 | **0.3 s** | **0/15** | 秒完成、全错 |

服务日志里同期有 **63 次 `429`**。

**根因**：`HttpTransport.ask` 把非 200 响应变成
`{"error": "HTTP 429", "knowledge_hit": False}` —— 限流被记成"这题答错 / 答非所问"。
于是报告会显示"模型退化"，而实际是**评测自己把配额打满了**。

## 三、修复（`1f0xxx` 之后的行为）

- 429/503 ⇒ **指数退避重试**（2s → 4s → 8s，最多 3 次）；
- 仍失败 ⇒ 抛 `TransportError`，runner **中断并打印**：
  ```
  ✗ 评测中断：评测被限流/过载打断（HTTP 429）：请调高 RATE_PER_MIN 或降并发，
    不要把这个结果当成模型退化。
  ```
- 其它非 200（400 等）不重试，保持原样。

**实测验证**：起一个 `RATE_BURST=1 / RATE_PER_MIN=1` 的服务跑 3 题——
18.3 秒后退出码 1，输出上面那句，不再产出 0/15 的假报告。

## 四、延迟漂移（README 的 2.8s）

干净 run 的逐题 `took_ms`（campus，n=20）：

```
p50 = 3104 ms
p95 = 4284 ms
max = 4798 ms
mean = 3131 ms
```

**结论**：
- README 原来写的"约 2.8 秒"是**早期单次测量**，现在实测 p50 ≈ 3.1s、p95 ≈ 4.3s；
- 漂移主要来自**上游模型端**（同一输入同一进程，逐题 2.5–4.8s），不是本地检索（检索 p95 7.6ms）；
- 因此 README 改成 **p50/p95/max + 样本量 + 条件**，不写单一"恒定值"。

## 五、评审两条建议的结论

| 建议 | 结论 |
|---|---|
| 调高 `RATE_PER_MIN` 跑评测 | **对**，但更关键的是"限流不能静默变成失败题"——已改成重试+中断 |
| 查清 2.8s → 4.7s 漂移 | **已查清**：p50 3.1s / p95 4.3s / max 4.8s（n=20，干净一轮）；README 已改成区间 |
| 改异步（收益低） | **同意不改**：瓶颈是模型端 3 次调用/题，不是线程模型 |
